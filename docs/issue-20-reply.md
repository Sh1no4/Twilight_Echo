感谢建议！这个方向我们已经在推进，并已按可行性分阶段落地了第一版实现。现状如下：

## 已实现（已合并到 `1.1.3`）

**协议支持**

| 协议 | 实现方式 | 状态 |
| --- | --- | --- |
| WebDAV | 纯 HTTP（PROPFIND/GET），匿名直连播放 / 认证走缓存下载 | ✅ |
| FTP / FTPS | `basic-ftp`（被动模式、显式 TLS） | ✅ |
| SFTP / SCP | 系统 OpenSSH `sftp`（密钥认证） | ✅（`ssh2` 因可选原生依赖 cpu-features 编译问题不可用，已实测并记录） |
| SMB | Windows `net use` / Linux `gio mount`（匿名/已缓存凭据） | ✅ |
| NFS | Linux `mount -t nfs`（运行时需 root） | ✅ |
| DLNA / UPnP | ContentDirectory 浏览 + res 直连播放 | ✅（投送到渲染器沿用现有 castBackend） |
| AFP | 建议通过系统挂载使用 | 未内置（见下文） |

**能力**

- 网络源管理：连接向导、连接测试、书签
- 目录浏览 + 播放 / 加队列 / 播放全部
- 虚拟媒体库：递归入库、持久化索引、搜索、元数据（标题/艺术家/专辑/时长）与封面提取与展示
- 下载缓存：统计与清理
- 统一搜索并入网络媒体库（本地库页可直接播放）
- 凭据安全：口令/私钥口令经系统安全存储加密，设置快照不含明文；路径穿越/异常输入校验；结构化错误码

## 验证状态

- lint / typecheck / 专项测试（含各协议 seam 级集成测试）全绿，生产构建通过
- ⏳ 真机验证待做：系统命令类（SFTP/SMB/NFS）与 SOAP 类（DLNA）依赖真实环境，已提供逐协议验证清单（`docs/network-music-sources-verification.md`）

## 已知限制 / 后续计划

- SFTP 仅密钥认证；SMB（Linux）与 NFS 需要系统挂载能力（root / gvfs）
- AFP 暂不内置协议栈，建议系统挂载后以本地目录添加
- DLNA 直连播放依赖媒体服务器 res URL 可达性，需要认证的流暂不支持
- 后续可做：媒体库与本地库更深度整合、断点续传、目录增量刷新

详细设计与排期见 `docs/network-music-sources.md`。欢迎参与真机验证或提供测试环境。
